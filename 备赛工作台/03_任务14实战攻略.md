## 1 先知道这题要完成什么

场景有两台机器人：星海图 R1（轮式）和宇树 G1（双足），相机均在头部。桌1有香蕉、柠檬、草莓、苹果；桌2有长颈鹿、斑马、大象、犀牛玩具；桌3有蓝、绿、红、黄收纳盒。一条语音指令要求机器人去三张桌子，抓两个道具，放进各自指定颜色的盒子，回初始位置并语音报告。

平台已经提供地图、航点、Nav2 配置、手眼标定、YOLO 检测模型、GraspNet 抓取模型、双足走路模型和 MoveIt2 配置。这题主要是调用并集成这些能力，任务14本身无需重新训练这些模型。依据：《任务14指导书》p1。

| 每台机器人的节点 | 通俗理解 | 输入 | 输出 |
|---|---|---|---|
| master | 调度员，记住现在做到哪一步 | 语音、完成消息、视觉返回值 | 导航命令、抓取命令、放置命令、视觉请求 |
| nav | 负责去指定位置 | 航点名称 | 到达后的完成消息 |
| vision | 负责找出物体或盒子在哪里 | 彩色图、深度图、查找目标 | 物体点云或盒子位姿 |
| arm | 负责抓取与放置 | 点云/位姿、哪只手 | 动作后的完成消息 |

节点不是函数。每个节点里有多个函数；回调函数是“某件事发生后由系统调用”的函数。话题像发送通知，服务像提出问题后等待答案。TF 是把相机看到的位置换算到机器人基座坐标系。

## 4 从空白开始的搭建顺序

下面是备赛建议顺序，不是官方强制步骤。

1. 进入任务14，先读实验要求与评分页，再点底部“ROS节点编写/编辑”。
2. 打开“配置文件和其他资源”，查看两机器人的手眼标定、地图/航点、模型及规划资源。记录本次平台中真实文件名和参数。
3. 先在 R1 的4个节点创建变量和自定义函数；再创建消息发布者、订阅者、视觉服务端。这样后续下拉框里才有可选对象。
4. 完成 nav、vision、arm 的局部功能，再连 master 状态机。
5. 每个指令打开齿轮补全参数并确认；每个函数检查入口、连接、分支顺序并提交。
6. 提交节点后进入仿真，从第一个失败环节调试。完整跑通R1后再把节点内容复制到G1并逐项修改差异。
7. 两台机器人都仿真后查看并保存报告。官方指导书的后续末步是“提交实验”查看最终分项；**本轮停在报告，不执行这一步锁定评分**。

依据：指导书p3–6讲节点、函数、复制、指令、变量和提交；p7–9讲仿真、调试和实验提交。只有条件判断允许多条出线，其他指令只允许一条出线。参数没填齐会发红光。条件分支的条件与连线顺序设置后不要随意对调。

## 7 master 调度员怎么工作

### init 与唤醒

`init` 顺次连接：设置唤醒词 → 创建 `_nav` 发布者 → 创建 `_grab` 发布者 → 创建 `_deploy` 发布者 → 创建 `_finish` 订阅者。R1 唤醒词为“你好小星”，回调绑定 `set_wakeup_keywords_callback`；完成消息绑定 `nav_arm_finish_callback`。

唤醒回调顺次连接：提取任务信息存入字典 → 发布静态TF → 将状态设1 → 发布 `_nav`，目标取字典 `target1-1`。

| 字典 key | 含义 |
|---|---|
| target1-1 | 第1个导航点名 |
| target1-2 | 第1个抓取对象名 |
| target2-1 | 第2个导航点名 |
| target2-2 | 第2个抓取对象名 |
| target3-1 | 第3个导航点名 |
| target3-2 | 第1个抓取对象对应盒子颜色 |
| target3-3 | 第2个抓取对象对应盒子颜色 |
| target4 | 第4个导航点名，即返航目标 |

证据：image5、7–15、21；字典完整说明见 image13。必须选择字典里的具体 key，不要把整个字典发成航点名。

### 完成消息驱动的8个分支

`nav_arm_finish_callback` 判断的是 `master_work_status`。按截图分支从左到右为1、3、4、6、7、9、11、12。先更新状态，再发下一条指令/请求，能避免快速回调到来时仍停在旧状态。

| 收到完成消息时状态 | 它表示什么已完成 | 先改为 | 然后执行 |
|---:|---|---:|---|
| 1 | 到达第1桌 | 2 | `_locate`：物体，target1-2，回调1 |
| 3 | 第1次抓取 | 4 | `_nav`：target2-1 |
| 4 | 到达第2桌 | 5 | `_locate`：物体，target2-2，回调2 |
| 6 | 第2次抓取 | 7 | `_nav`：target3-1 |
| 7 | 到达第3桌 | 8 | `_locate`：颜色，target3-2，回调3 |
| 9 | 第1次放置 | 10 | `_locate`：颜色，target3-3，回调4 |
| 11 | 第2次放置 | 12 | `_nav`：target4 |
| 12 | 返回初始位 | 0 | 文字转语音“任务顺利完成”（截图顺序是先播报再清零） |

最后一行按截图连接“文字转语音→状态清零”；其他行都是状态更新后发请求。不要误把2、5、8、10做成 `_finish` 分支，它们是在等视觉服务返回。

证据：image16–34、image17为总流程。状态值是这套第三方实现的编号，不是官方要求必须用这些数字。

## 8 nav 先学会一去一回

`init`：初始化航点 → 创建 `_finish` 发布者 → 创建 `_nav` 订阅者，绑定 `nav_target_message_callback`。

导航请求回调：`nav_navigation_name = 回调 Navigation_Address` → 判断 `nav_navigation_status == false` → 置忙标志为1 → 导航到航点（目标取 `nav_navigation_name`，完成回调 `nav_finish_callback`）。

导航完成回调：忙标志设0 → 发布 `_finish` 完成标志为1。

G1 的 init 在初始化航点后增加“加载走路模型”：`walk.rknn`，速度话题 `/cmd_vel`，里程计话题 `/odom`。证据：image47–58、116–117。

验收：调试面板能看到接到正确航点名，忙标志从0到1再回0，完成消息随后触发 master 的下一步。如果只到达却不继续，优先检查完成回调和 `_finish`，不要先改地图。

## 9 vision 分清物体点云和盒子位姿

`init`：订阅彩色图 → 订阅深度图 → 创建 `_locate` 服务端。两个图像回调分别把 `color_image`、`depth_image` 保存到对应节点变量。

视觉请求回调按 `Detect_Type` 分两支，截图中的值为“物体”“颜色”。

**物体分支：**

1. 目标检测：图像选 `Vision_Color_Image`，模型 `yolo.pt`，对象名读回调 `Detect_Name`，输出选择“矩形检测框”，存 `Vision_Box`。
2. 深度图转点云：深度图选 `Vision_Depth_Image`，截取区域 `Vision_Box`，输出 `Vision_Point_Cloud`。
3. 服务端响应 `_locate`：`Point_Cloud` 读 `Vision_Point_Cloud`。若界面要求同时设置 `Pose`，按实际参数要求设置，后续抓取回调只消费点云字段。

**颜色分支：**

1. 颜色检测：彩色图 `Vision_Color_Image`，颜色读 `Detect_Name`，输出“中心位置”，存 `Vision_Point`。
2. 二维点转三维点：二维点 `Vision_Point`，深度图 `Vision_Depth_Image`，输出 `Vision_Pose`。
3. TF坐标变换：把 `Vision_Pose` 从该机器人相机系转为“基座”。
4. 服务端响应 `_locate`：`Pose` 读 `Vision_Pose`。下游放置回调使用这个基座系位姿。

证据：image59–76；完整分支图见 image68。**物体分支不在这里变换点云。** 这点是第三方文字说明的重要错误；应以图核对。

验收：物体分支拿到非空目标点云，颜色分支拿到对应盒子的位姿，两个分支都确实执行到“服务端响应”。卡在状态2/5/8/10时优先看服务有没有返回、模型和对象名有没有选对。

## 10 arm 抓和放必须用同一只手

`init`：初始化规划组 → 创建 `_finish` 发布者 → 创建 `_grab` 订阅者绑定抓取回调 → 创建 `_deploy` 订阅者绑定放置回调。

抓取回调首先：`Grasp_Point_Cloud = 回调 Pcloud`，再判断 `Hand`。R1 图中分支1=false/0，用 `left_arm` / `left_gripper`；分支2=true/1，用 `right_arm` / `right_gripper`。

每条抓取分支依次：设置 `Grasp_Hand` 和 `Arm_Hand` → 抓取位姿估计（`graspnet.tar`，输入 `Grasp_Point_Cloud`，输出 `Grasp_Pose1`）→ TF变换 `Grasp_Pose1`，从相机系到基座 → 机械臂移动（臂读 `Arm_Hand`，位姿读 `Grasp_Pose1`，截图速度100%，回调 `grab_finish_callback`）。

抓取完成回调：闭合夹爪，夹爪读 `Grasp_Hand` → 发布 `_finish = 1`。

放置回调：`Grasp_Pose2 = 回调 Fpose` → 按同样的 `Hand` 映射设置机械臂与夹爪 → 机械臂移动到 `Grasp_Pose2`，截图速度100%，回调 `deploy_finish_callback`。这里的位姿已经在视觉颜色分支转成基座系，不再重复变换。

放置完成回调：张开夹爪（截图开度80%，夹爪读 `Grasp_Hand`）→ 发布 `_finish = 1`。

证据：image77–109。图82为抓取流程，84为分支定义，85/86为左手分支，90/91为右手分支；95–102为放置分支；103–109为完成回调。

这里的100%速度、80%开度是该第三方仿真设置，不能外推为真实机器人安全参数。练习应先按本场景与平台可选值核对。

## 12 用状态定位错误

| 仿真现象 | 先看什么 | 最小检查 |
|---|---|---|
| 唤醒后完全不动 | master唤醒回调是否执行 | 唤醒词、回调绑定、字典是否有8个key、状态是否到1 |
| 状态1/4/7/12长时间不变 | nav | 航点名、忙标志、导航完成回调、`_finish` 发布 |
| 状态2/5/8/10长时间不变 | vision服务 | `_locate`是否建成服务；请求字段名；检测分支；服务响应 |
| 状态3/6不变 | arm抓取 | `Pcloud`取值、graspnet模型、TF源和目标、机械臂完成回调 |
| 状态9/11不变 | arm放置 | `Fpose`与位姿系、实际持物手、张开夹爪和完成发布 |
| 夹爪伸向奇怪位置 | 坐标系 | 是否对同一数据做了两次相机→基座变换；是否用了另一机器人的TF |
| 第1物抓了却放不下 | 手编号 | 第1抓取与第1放置Hand相同；发送与分支映射一致 |
| R1成功、G1不动 | G1差异 | 是否加载walk.rknn，话题是否正确，唤醒词是否更改 |
| 机器人看起来完成但分数没更新 | 区分过程报告与最终成绩 | 先查节点保存、重新仿真和报告版本；本轮未提交最终评分，因此不能要求最终分数更新，也不为取分锁定实验 |
| 节点编辑分不足 | 结构报告 | 空节点、自定义函数、变量、遗漏指令/参数、核心配置查看 |

依据：指导书p8调试面板能查看全部节点函数执行过程与变量当前值；p9提交实验后查看成绩。表中排查优先级为依据结构给出的备赛建议，不是平台已实测故障清单。
