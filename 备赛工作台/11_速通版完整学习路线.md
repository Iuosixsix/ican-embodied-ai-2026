## 3. 运动控制：先分清五个旋钮

机器人每一步先读取观察，再输出动作，环境根据结果给奖励；训练算法根据经历改进策略。训练完成后的推理，用现有策略执行动作。训练结束、仿真正常、最终评分、自己能重做是四个独立结论。

| 配置 | 它决定什么 | 选错后常见表现 | 平地走路例子 |
|---|---|---|---|
| 观察值空间 | 策略能获得哪些信息 | 不知道身体倾倒、转弯或关节状态 | 躯干姿态/速度、关节角/角速度、目标速度、步态相位 |
| 动作空间 | 输出什么、怎样变成执行指令 | 抖动、过冲、动作幅度异常 | 输出关节目标角，低通滤波+前馈，再按需要限幅 |
| 奖励 | 哪些行为值得学、哪些应受罚 | 只站着、跑偏、追速度而倒地 | 存活、速度跟踪、姿态稳定、横向偏移处罚 |
| 重置条件 | 一段交互何时结束、重新开始 | 条件过严频繁重置，或倒地后持续无效动作 | 倾角超过阈值、达到设定步数 |
| 训练参数 | 怎样更新策略、学多久 | 收敛不稳、学不充分或更新效率差 | 学习率、batch、网络结构、折扣、采样/更新配置 |

“输入全选”只适用于已核对的某个任务页面。行走、跑跳和舞蹈的观察目标不同；舞蹈参考不选躯干线速度和参考轨迹编码，是因为该实现把轨迹用于动作前馈，不能据此说所有舞蹈算法都不需要轨迹信息。

算法名先理解到能区分职责：Q-learning用动作价值选择动作，DQN用神经网络估计这类价值；Actor-Critic把给动作的策略与评价回报的价值估计分开，PPO则用受约束的策略更新改进动作选择。本次运动练习的重点是PPO策略配置及效果，第一遍不必推导整套算法，但要知道“策略网络执行动作”和“训练算法更新网络”是不同环节。

训练环境也影响策略。地形、摩擦、质量、外力和IMU噪声随机化，让模型在一组变化条件下学习，减少只适应单一仿真场景的问题；这与仿真到真实环境的差异有关。机器人碰撞模型简化用于降低计算负担，需要与场景精度要求权衡。第一轮培训提到正式题可能开放环境配置，不能只背训练参数而漏掉这些入口。

### 行走、跑跳、舞蹈分别在学什么

- **行走：** 接收目标前进速度和旋转速度，速度为零时能站稳；还要能按指令转向。导航最后给出的速度可以接到这类控制器。
- **跑步与跳跃：** 当前练习要求持续向前，不需要与行走相同的动态转向指令。前进奖励还应考虑横向偏移；跑和跳的垂直运动鼓励程度不同。
- **复杂地形：** 在坡、坑洼等变化下仍稳定，不能用平地站稳证明通过。
- **舞蹈：** 同时保持身体稳定、跟随预设轨迹。只奖励存活可能学到站着不动；只有动作跟随而缺乏稳定约束则可能跳到一半摔倒。

当前任务1示范基线采用关节目标角、低通滤波+前馈；走路有限幅、跑跳无约束；跑步后期垂直速度奖励×2、跳跃×4。三种基线训练参数为2000W总步数、学习率0.0001、熵系数0.005、batch2048、3层、每层512、gamma0.995、单次交互参数1000。它们是本账号本轮基线，不能推广为任何场景的唯一答案。原配置与本次报告在08，之后新实测以12为准。

### 看到源码时，先找“实际怎么用”，再看注释

| 字段 | 正确理解 | 本次显示源码的例子 |
|---|---|---|
| 平滑系数 | 当前输出与旧输出的加权比例 | `0.9×旧动作 + 0.1×新动作`；它不是学习率 |
| 动作增益与前馈 | 把网络输出缩放，并加上步态模板 | `kb`用于动作缩放；`dh`等参与前馈，不能因注释就当物理阻尼 |
| 驱动刚度/阻尼 | 关节实际追踪目标角时的响应和抑振 | 本次走路调用链中的`xDrive.stiffness/damping`为500/50 |
| 步态相位周期 | 动作的节奏，与物理更新步长关联 | `T1=30`、步长0.01s、两组腿循环到`2*T1`，完整周期约0.6s |
| 奖励公式 | 训练过程中每步获得的优化信号 | 存活和跟踪基项减去倾角、速度误差、横向漂移等处罚 |
| `buffer_size`与`batch_size` | 更新用的经验规模与每批样本规模 | 示例20480与2048，不能当成同一项 |
| PPO `epsilon` | 限制策略更新获益区间的裁剪参数 | 示例0.2，同时还有调度，不能假定始终不变 |
| `gamma` | 当前时刻如何折算更远未来的奖励 | 越远未来乘更多次gamma，不是越接近训练成功环境奖励自动越少 |
| `lambd`与`num_epoch` | 优势估计相关参数、对采集经验更新的遍数 | 本次源码示例0.95与3；它们不是gamma，也不是整个任务只训练3轮 |
| 归一化与调度 | 输入尺度处理、训练过程中参数怎样变化 | `normalize`、学习率/熵系数/裁剪的调度需结合源码解释 |
| 回合步数与总训练步数 | 单次交互结束条件与全程训练预算 | `tt>1000`不等于总训练只做1000步；也不等于网页等1000秒 |

本次行走显示源码的奖励可读为：

```text
每步奖励 = 3
         - 0.1×X倾角 - 0.1×Z倾角
         - 2×|实际角速度－目标角速度|
         - 2×|实际前进速度－目标前进速度|
         - |横向速度|
```

这是对平台显示源码的解读，**不是正式评分公式**。界面源码已发现与部分对照配置不一致的情况，不能仅凭展示文本认定后台实际怎样训练；以配置、模型、运行报告的对应证据研究效果。

### 运动题怎样读报告

任务1要分别检查站立、走动、原地旋转、正常姿势、跑跳速度和方向；官方构建52分、推理48分，各类至少2模型并查看。任务2检查正常走、上坡、下坡坑洼、1.3m/s和稳定流畅；至少2模型并查看。任务3检查15秒动作完成、轨迹偏差和训练步数档位；官方只明确至少2模型，不能自行扩大成每种舞蹈都强制2个。

**任务3不是训练越久，该分项得分越高。** 官方口径是在完成15秒舞蹈基础上，训练用一亿步得10分、两亿步得5分；实际与预设动作的位置偏差在8%以内得10分、12%以内得5分。两项分别按档位检查，同一项的档位不叠加；不要自行补造指导书未写明的中间步数插值规则。详见[10 官方任务要求与评分](10_官方任务要求与评分.md)。

速度、偏差和训练步数可能是分档；不要把所有档位分数同时相加。最短排错顺序是：**目标/模型有没有选对 → 观察与动作结构 → 奖励/重置 → 训练参数 → 新仿真结果**。不要一看到摔倒就把学习率、步数和奖励一起改掉。

## 4. 视觉：输出类型决定后面怎么接

| 方法 | 输入与输出 | 对应任务 | 后续怎么用 |
|---|---|---|---|
| 图像分类 | 一张图→类别及置信度 | 4表情 | 判断整张图是什么表情 |
| 目标检测 | 图像→目标类别、矩形框、置信度 | 5；10；14预置模型 | 从大图找到目标位置，再截取相关区域 |
| 实例分割 | 图像→每个物体的像素掩膜/边界和类别 | 11、12 | 抠出单个物体的深度，减少相邻物体混入点云 |
| 视频分类 | 一段视频→动作类别 | 6的TSM流程 | 利用随时间变化的模式识别动作 |
| 姿态规则 | 关键点序列→关系/距离/角度条件→动作判断 | 6个性化流程 | 用明确的关节几何与时序条件判断行为 |
| 颜色检测 | 图像→指定颜色区域/中心 | 10—12、14放置区 | 定位颜色收纳盒；纯色任务不必重新训练网络 |

检测框只告诉你物体在图像哪里，不能直接当作机械臂三维坐标。分割更细，但也不自动得到深度；深度和坐标变换在抓取段继续处理。

### 数据、训练、推理三段必须衔接

1. **数据：** 分类标整图标签；检测为每个目标分别画贴合的矩形；分割核查每个实例边界再打标签；视频按整段行为标注。类别要覆盖，目标不能漏，标签含义一致。
2. **增强与预处理：** 裁剪、缩放、亮度/颜色扰动等用于覆盖合理变化；不能破坏任务语义。把“6”翻成“9”、把需识别文字翻转后仍沿用旧标签，都会引入错误。推理尺寸和标准化应与模型要求一致。
3. **训练：** 选择正确数据集、模型、优化器、学习率、batch、workers、epoch、分类头。batch是每批多少样本，workers是数据加载并发，epoch是遍历训练数据的轮次；它们不能互相代替。
4. **绑定：** 推理节点实际选择刚刚验证的权重；类别数/顺序与输出一致。7类表情不能配4类头；换了数据集或权重后要重新核对。
5. **验证：** 先看模型指标，再让完整流程跑全部指定输入。一个模型指标高，但裁剪错、图库错或根本没选该权重，应用仍会失败。

训练集用于学习，验证集帮助比较和选择配置，测试集用于检验未参与训练的数据表现；当前平台内置了划分，不要自己假设看到的每张测试图都来自训练集。曲线要结合验证结果看：训练越来越好而验证不改善，可能是过拟合；两边都差还要查标注、输入、模型和训练配置，不能把任何曲线形状当唯一诊断。若使用量化，目的是减小存储/计算开销，但必须重新比较准确性和完整流程表现；模型变小不等于当前题目一定更优。

### 指标到底在问什么

以“是否检测到危险品”为例，TP是正确检出的目标，FP是误报，FN是漏掉的目标。

| 指标 | 它衡量什么 | 不能替代什么 |
|---|---|---|
| Accuracy | 全部样本中预测正确的比例 | 类别不平衡时不能单靠它判断漏检风险 |
| Precision | `TP/(TP+FP)`：报出来的有多少是真的 | 高precision不保证没有漏检 |
| Recall | `TP/(TP+FN)`：应找的有多少被找到了 | 高recall不保证没有大量误报 |
| F1 | precision和recall的调和平均 | 不表示每个类别都已达到相同水平 |
| mAP | 对检测结果的precision-recall表现计算AP，再按类别平均 | 不等于某张图上一个框的置信度；具体IoU口径看平台说明 |
| 单次置信度 | 模型对本次预测的评分 | 不是整个模型的准确率，也不保证这一次真的正确 |

任务4最好模型accuracy>0.8对应模型质量项；任务5要求precision、recall、F1、mAP分别>0.8；任务6accuracy>0.9对应模型质量项8分。**这些是各题的分项要求，不是所有视觉任务统一合格线。** 仿真、数据覆盖、节点配置另外计分。任务5低端零分阈值原PDF仍为“XX”，不要补猜。

### 三道视觉题，按这条线理解

**任务4：明/暗两套表情流程。** 明亮图通常走“采集→尺寸→标准化→分类”；暗图在前面补适当亮度处理。参考输入224，7类头；均值/标准差按当前模型配置。至少20图覆盖7类，每套内置7类均测试；最终仿真有10次表情和光照变化。检查类别、置信度以及到底走了明亮还是昏暗流程。

**任务5：一个检测基础，三种应用。** 危险品是“采集→尺寸→检测”；陌生人是“检测人脸→裁剪人脸→与家庭图库比对”；仪表读数是“检测文字区域→裁剪→OCR”。官方指导书要求电子屏标注框住屏幕上的文字，不能只画整个外壳。至少20图覆盖刀具、药片、人脸、屏幕相关目标，三应用全部仿真。第三方人脸阈值0.40与培训参考0.8不同，先用有出处的基线，再同时测试熟人识别和陌生人误认，不能只测一个方向就下结论。

**任务6：学习型和规则型各做一套。** TSM根据视频时序判类别；规则型先提人体关键点，再看头部、手腕、髋、脚踝的关系及变化。例如攀爬可能涉及头部上移、手脚交替及肘肩髋夹角变化；具体条件需对当前图像坐标方向和目标动作核对。官方4类应用场景是久坐、室内锻炼、跌倒、危险处攀爬，均要验证；“模型能认跳绳”不能代替跌倒/攀爬流程的验证。

**本轮实测差异（2026-10-23）：** 标注下拉有5项：摔倒、跳绳、俯卧撑、打字、攀爬；TSM训练分类头下拉实测只提供1、2、3、4。本轮实际标注四种训练动作——跌倒（页面标签“摔倒”）、跳绳、俯卧撑、打字，各5段，共20段，训练分类头为4。跳绳、俯卧撑同属室内锻炼场景，打字也不能直接等同于已经完成久坐判断，所以**4类应用场景、4个训练动作与5项标注菜单不是一一对应**；不能因为菜单有5项就强行使用5分类头。TSM推理节点只有权重和CPU等设备选择，没有独立分类头输入；攀爬在本轮路线中走个性化姿态链，当前规则与正负例结果见下段及[12实测手册](12_全任务实测与排错手册.md)，仍需改善质量并复测。这是当前页面与本账号配置的实测记录，不改写官方四类应用要求和评分。

**真实失败案例：** 当前模型accuracy为0.95407，但第一轮四场景3D中的摔倒三条采样输出分别是“摔倒”0.53、“跳绳”0.33、“俯卧撑”0.35；打字虽然5条类别一致，置信度只有0.28—0.42。因此高验证指标与100%运行进度都不能替代应用质量。个性化规则在climb1和3D攀爬中四条全true，在climb2却有头部条件false；打字负例的`outputs`也仍写“攀爬”，但match为0.5、头部与双脚条件false。判断时看match及逐条规则，不能只看输出标签。两流程、四通用内部测试、三姿态对照和四场景报告现均已取得，最终评分未提交；下一轮需改进摔倒混淆、低置信度并复测正负例。详情与证据见[12 全任务实测与排错手册](12_全任务实测与排错手册.md)。

任务5训练可参考官方培训给出的YOLO、batch1、workers0、SGD、lr0.001、150epoch、L模型，以及Mosaic/HSV/缩放/翻转增强；这是明确说明“非唯一答案”的组合。真正的判断依据是本题数据、模型四指标和三条应用的实际输出。

## 5. 导航：地图告诉你哪里能走，定位告诉你现在在哪

| 部分 | 解决的问题 | 典型输入→输出 | 常查参数 |
|---|---|---|---|
| SLAM建图 | 环境长什么样，同时估计运动 | 雷达/IMU等→地图与位姿估计 | 算法、扫描/更新参数、建图路线 |
| AMCL定位 | 已有地图上我在哪里 | 地图、雷达、里程计→当前位姿估计 | 粒子数、更新距离/角度、传感器匹配 |
| 代价地图 | 地图上的路对机器人是否安全可通行 | 静态地图+动态障碍+机器人形状→通行代价 | 半径、膨胀、观察源、范围/高度、刷新频率 |
| 全局规划 | 从当前地点到目标的大路线 | 起点、终点、代价地图→路径 | A*等规划算法、未知区域、目标容忍 |
| 局部规划/控制 | 下一刻怎么沿路径走并避开近处障碍 | 路径、当前状态、局部障碍→线/角速度 | TEB等、速度/加速度、目标容忍与权重 |
| 恢复行为 | 规划/运动卡住时怎样尝试恢复 | 失败状态→旋转、后退、等待等 | 使能项和相应速度/等待参数 |

A*是带启发式的搜索，不是深度优先搜索；不能把讲解中的简化口误背成算法定义。TEB负责局部规划，AMCL负责定位，它们各自做不同工作，不能互相替换。

### 任务7：先把地图建对

两个场景都先漫游，观察玻璃、重复房间、狭窄处和后续要去的工位。选算法同时要选路线；只调算法、不覆盖目标区域，地图仍会缺失。GMapping和Karto都有对应场景的参考配置，不能记成某个大小场景只能用其中一个。

算法比较先记住关注点：GMapping以粒子滤波建图，Karto属于图优化路线；LIO-SAM以激光与惯性信息构建优化关系，FAST-LIO强调高效激光惯性里程计，Point-LIO面向高频与快速/剧烈运动等条件。名字不同意味着参数意义也不同，不能把某算法的6个选项按位置抄给另一算法。培训中的“回环路线”只是机器人怎样走，系统是否做闭环全局优化仍要看具体实现。

仿真中检查覆盖是否全、墙是否重影/歪斜、门口是否保留、重复观测后是否一致。路线绕回已知区域与算法是否实现闭环优化是两个层面的事。官方小/大场景都计分，不能只完成小场景。PDF大场景分值有20/40文字冲突，按实际报告核对，不自行编一个总分公式。

### 任务8：航点既有位置，也有朝向

把目标放在能到达的位置，还要让机器人面向服务对象：迎宾朝门、介绍朝文化墙、送零食朝工位。两场景合计17航点、48策略参数。设置时考虑机器人半径，与门、墙、桌椅留出空间。

机器人半径近似表示身体占用区域；膨胀层提高靠近障碍区域的通行代价。膨胀过大可能把门口挤没，过小可能让路径贴障碍。局部代价地图围绕机器人滚动并更快更新，处理近处动态障碍；深度相机观察源可补充仅扫到桌腿的雷达信息，避免把桌面下方误判为可以穿过。

培训参考为检测范围5.5m、高度1.5m，全局1Hz、局部10Hz、滚动窗口开启，全局A*、局部TEB、旋转/后退/等待恢复。实际配置要结合场景与报告，不能声称这些参数在所有场景最好。官方表头仿真60分与明列51分到点/最多扣9分之间存在口径缺口，不把猜测当评分事实。

### 任务9：为什么三维点云还要转换

PCD保留三维点云；PGM用于当前导航的平面栅格表达。转换要选高度区间、分辨率和离群点规则。分辨率太粗会丢细节，太细增加处理量；稀疏噪点可能被投影成假障碍，需要按邻域规则过滤。

本练习有抬高平台/台阶。若把台阶本身的低处点云压到平面，它会成为一条封路障碍。培训选择Z=1—2m，目的在该场景中是剔除台阶投影、保留上方桌椅等障碍，让机器人仍能上台阶。**过滤改变的是地图表达，不会凭空赋予机器人真实越障能力。** 换场景需要重新判断高度范围。

完成顺序为：完整漫游→生成PCD并预览→转换PGM并预览→设置10航点与朝向→30个导航参数→选择该地图实际验证。检查地图质量、到点和碰撞三个方面。培训提过正式题可能出现LIO-SAM或Point-LIO；练习FAST-LIO的参数不能直接套用其他算法。

仿真前一起核对**所选PGM、该地图的航点集和初始位置**，例如本轮任务9使用`nav9_pgm`、对应十点、充电桩初始位。报告写“到达”也不自动证明点位合理性得满分，实际结果与边界见[12实测记录](12_全任务实测与排错手册.md)。

导航最短排错路线是：**当前选中的地图 → 初始位姿/定位 → 目标点与朝向 → 障碍和半径/膨胀 → 全局路线 → 局部控制 → 恢复行为 → 完成通知**。有全局路径并不等于控制器一定能把机器人送到点。

## 6. 抓取：先说明“这个位置属于谁的坐标系”

图像里的`(u,v)`是像素；相机系中的`(x,y,z)`是空间位置；机械臂目标还需姿态。只有内参和一对像素坐标，不能唯一恢复物体三维位置，还需要深度、已知平面等约束。

在简单针孔模型、已正确处理畸变和深度单位的条件下，可理解为：

```text
相机三维点：X = (u-cx)×Z/fx，Y = (v-cy)×Z/fy，Z来自深度
基座三维点：p_base = R_base_camera × p_camera + t_base_camera
```

手眼标定估计相机与机器人相关坐标系的关系。眼在手上时，相机随末端运动，通常还要结合当前末端相对基座的位姿；眼在手外时，相机固定在机械臂外部，使用相机到基座的关系。**不要只复制矩阵里的数字，先写清每个矩阵的源坐标系、目标坐标系、方向和单位。**

先看每个矩阵字段指定的两个坐标系，不能把“相机—腕”移作“相机—基座”。任务14的头部相机随机器人本体运动；TF按当前节点语义使用，平台未明示的矩阵方向不自行标注或猜测。

15张标定图应有距离、位置、姿态变化：远中近、画面各区域、不同旋转。连续拍15张几乎一样的图，并不提供同样有效的几何约束。任务10第三方矩阵图片不完整，不能拼图补猜，更不能用单位阵冒充。

任务10的2D抓取accuracy不能替换成11/12的6D抓取四指标；这些是各练习的模型质量分项，不是正式省赛统一合格线，依据[10 官方任务要求与评分](10_官方任务要求与评分.md)。任务11/12的抓取位姿标注有4个场景、每场景5道具，每个默认姿态都要判断并调整；这不是说每个道具只标一个姿态。任务12标注中的5类/5道具与仿真的4道具属于不同环节。

### 实例分割为什么能帮助抓取

密集桌面上，矩形框可能同时包住目标和旁边物体；把整个框的深度变成点云，会混入别的物体。实例分割能更准确地挑出目标像素及其深度，再交给GraspNet估计抓取位姿。6D表示三维位置加三维姿态，描述的是夹爪如何抓，不只描述物体中心在哪里。

正样本应是可用的抓取姿态；碰撞、深度不合适或角度不合理的姿态要调整或标负，不能全部选正。任务11/12模型质量项包括：实例precision>0.95；抓取Top-1成功率S1≥0.75、Top-5成功率S5≥0.9、无碰撞率CFR≥0.85、打滑风险SLR≤0.20。前三个方向是越高越好，风险越低越好；达到这些仍不等于每个物体已实际抓放成功。

### 目标位姿有了，为什么还需要规划

**逆运动学IK**求“为了让末端到目标，各关节应是什么配置”；**规划器**考虑从当前配置怎样到那里以及中途碰撞；**执行器**才把轨迹落实到机械臂。IK解不等于无碰撞路径，也不自动意味着直线运动。

任务12需要把左右臂、左右手分成正确规划组，选对link；设左右臂初始、左右手开/合六种姿态；绑定手与手臂的末端连接关系。再配置IK求解器、规划器和来自点云/深度的碰撞环境。OctoMap表示三维空间占用，帮助检查桌面/盒子是否被当作障碍。先预览切换姿态，再拖目标预览规划执行，两个预览动作都不能漏。

抓放的通用顺序为：**初始姿态→拍照→找到目标与放置区→得到目标点云/抓取位姿→转换到执行坐标系→规划移动→合爪→移到放置处→开爪**。每一段都要确认数据来源；一次检测成功不能代替“抓取点合理、确实抓到、确实放入”三项结果。

## 7. ROS基础：用一个消息把下一步叫醒

任务13本次仍显示未发布，下面是完成集成需要的概念，不冒充它的官方实验步骤或分数。

| 概念 | 一句话解释 | 本任务里的例子 |
|---|---|---|
| Node节点 | 具有明确职责的运行单元 | master调度、nav导航、vision感知、arm抓放 |
| Topic话题 | 发布者发消息，订阅者收到后处理 | master通过`_nav`告诉nav去哪个航点 |
| Publisher/Subscriber | 消息发送端/接收端 | nav与arm发布完成，master订阅完成 |
| Service服务 | 一个请求对应一个返回结果 | master请求识别苹果，vision返回点云 |
| Callback回调 | 某个事件发生后执行的函数 | 收到导航命令、导航完成、视觉响应等回调 |
| State状态 | 当前正在等待哪个阶段 | 等导航、等识别、等抓取、等放置 |
| TF | 把同一几何量换成另一坐标系表达 | 相机中的抓取位姿转换到基座系 |

话题本身不会自动表示任务已经完成；必须另发完成消息。服务客户端也可以异步等待结果，不代表所有节点停止。TF只换表达，不会驱动机械臂；换好坐标后仍要发运动指令。

init中的“创建发布者/订阅者/服务”只建立通信入口；运行时还要执行“发布消息”或“服务端响应”才实际传数据。回调函数创建后还要绑定到对应事件，函数名存在不等于它会执行。

**数据线和控制顺序都要对。** 画布连线表示执行关系，但不会自动修正字段名、类型、变量、回调或数据坐标系。流程看起来连成一条，仍可能在运行时拿到空变量。

## 8. 任务14：先调用现成能力，再调通任务顺序

### 8.1 四节点先约定接口

| 通信 | 发送→接收 | 字段和用途 |
|---|---|---|
| `_nav`话题 | master→nav | 字符`Navigation_Address`，目标航点名 |
| `_grab`话题 | master→arm | 布尔`Hand`；点云`Pcloud` |
| `_deploy`话题 | master→arm | 布尔`Hand`；位姿`Fpose` |
| `_finish`话题 | nav/arm→master | 本账号已存字段为布尔`is_Finish`；发送端和接收端名称、大小写、类型保持一致 |
| `_locate`服务 | master请求→vision响应 | 请求`Detect_Type`、`Detect_Name`；返回`Pose`、`Point_Cloud` |
| 彩色/深度图话题 | 相机→vision | 保存到彩色图和深度图节点变量 |

特别容易混淆的一条：**服务返回`Point_Cloud` → master写入抓取消息`Pcloud` → arm读取`Pcloud`保存成`Grasp_Point_Cloud`**。字段不会因为中文意思相同就自动匹配。

vision初始化应是两个相机订阅者加一个`_locate`服务端，不能把服务建成普通订阅。nav收到目标时设置忙标志；到达回调必须清忙并发布完成。arm抓取移动完成后闭爪，再发布完成；放置移动完成后开爪，再发布完成。

**本账号已验证的保存依赖：** 先保存master的发布者，再配置nav订阅者。本轮nav菜单起初只有`_finish`；保存master发布者后才出现`_nav/_grab/_deploy`。续做已有配置时沿用`_finish.is_Finish`，不要另造不同大小写的完成字段；新题若采用其他字段则按题内定义保持两端一致。证据和过程见[12任务14实测](12_全任务实测与排错手册.md)。

### 8.3 两条视觉分支的坐标不同

**查物体：** 彩色图检测目标框 → 按框截取深度并转目标点云 → 服务返回相机系点云。arm接着用GraspNet估计相机系抓取位姿，再做相机→基座变换，然后移动抓取。参考实现不在vision物体分支先做同一个TF。

**查颜色盒子：** 颜色检测出中心像素 → 结合深度得到空间位姿 → 在vision转换到基座系 → 服务返回`Pose`。arm接收的放置位姿已经属于基座系，不再重复相机→基座变换。

防错方法：给每个中间变量旁边写“类型/坐标系”。同一变换不能对同一数据重复做；必要的相机→末端→基座多级变换可以合法串接，关键是每一步输入输出系相接。

### 8.4 手别和R1/G1复制检查
